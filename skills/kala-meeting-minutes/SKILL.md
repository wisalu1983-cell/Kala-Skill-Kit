# Kala-MeetingMinutes

## 概述

把会议纪要当作“证据驱动的内容产品”，而非一次摘要生成。先证明内容来自哪里、范围是什么、哪些已经决定，再决定如何排版和发布。

核心完成标准：关键结论可追溯、待办可执行、未定内容不冒充结论、视觉关系可读、内容出现在正确位置、发布结果经过回读。

## 依赖与能力边界

- 本地包验证器需要 Node.js 18+，不依赖 npm。
- 输入或输出涉及飞书时，**REQUIRED SUB-SKILL: Use kala-feishu**。让它负责 OAuth、账号路由、文档块、图片、画板和云盘操作。
- 不复制或绕过 `kala-feishu` 的 token、权限与删除规则。
- 找不到 `kala-feishu`、授权无效或目标不可写时，不声称飞书交付完成；转为本地待发布包。

## 何时不要使用

- 只要逐字转写、不需要提炼或排版：使用转录工具即可。
- 只编辑普通文档且与会议无关：使用对应文档 Skill。
- 用户只问某一段会议内容，不需要形成纪要：直接回答并引用原文。

执行任务前按需读取：

| 场景 | 必读文件 |

## 工作流

### 1. 输入与权限预检

先列出已获得和缺失的输入：

- 完整转录文本、音频或可访问链接；
- 会议日期、主题、参与人和说话人映射；
- 用户强调的时间范围、目标、术语和专有命名；
- 样例纪要及其对应完整转录；
- 白板、截图、SVG 或其他视觉素材；
- 目标飞书 URL、账号/租户、目录和修改语义。

只有链接但无法读取原文时停止，要求用户导出或粘贴文本。不要根据标题、白板照片或旧纪要猜整场会议。

若用户没有明确“新建、重写、替换、追加”，先读取目标文档结构，再用一句话确认修改语义。位置歧义会改变最终结果，不能自行决定。

### 2. 锁定用户约束

建立本次任务的约束表，至少包含：

- 当前重点与明确排除的范围；
- 说话人真实姓名；
- 术语、角色与项目名的统一写法；
- 用户已确认的视觉媒介；
- 必须保留的原图、完整转录或参考内容；
- 目标文档和目标位置。

后续用户纠正会覆盖旧推断。每次纠正后同步更新约束表和受影响的内容，不只改用户指出的那一句。

### 3. 反推样例方法

用户提供“样例纪要 + 对应完整转录”时，先研究样例如何从原文得到成品：保留了哪些事实、压缩了哪些讨论、如何表达结论与待办、栏目顺序、章节粒度、金句标准、视觉组件和完整转录位置。

只迁移方法、结构和视觉规则。样例中的事实、人员、日期、待办和结论不能进入新纪要。

### 4. 建立证据账本

按 `references/content-workflow.md` 处理完整转录，形成带时间戳和说话人的证据项。把内容分类为：事实、观点、已确认结论、倾向方案、待办、开放问题、后续范围、原话候选。

关键结论和待办没有证据时不得标记为已确认。白板可帮助理解结构，但文字难辨或逻辑不清时优先用转录佐证；仍无法判断就标为未确认并问最小问题。

### 5. 先定主线，再写栏目

用会议目标和用户范围约束写一句主线。所有栏目都服务于这条主线：

1. 总结；
2. 关键结论；
3. 待办；
4. 智能章节；
5. 关键决策与金句；
6. 相关资料；
7. 完整转录。

栏目是否出现取决于样例和用户要求，但不能用摘要替代用户要求保留的完整转录。

### 6. 生成内容稿

写作时：

- 用协作者能直接理解的名称替代含糊内部称呼；
- 区分“讨论过、倾向、已确认、尚未决定”；
- 待办优先写负责人、动作、期限、依赖和验收方式；
- 未给负责人或期限时写“待确认”，不要补造；
- 金句必须来自原文，短引文遵守来源与版权要求；
- 章节标题描述议题，不机械复述每句话；
- 未来阶段只保留与当前决策有关的边界，不抢占当前重点。

### 7. 视觉与位置规划

先写 `publish-plan.json` 或等价操作清单，再改文档。对每项视觉内容记录：信息目的、媒介、目标位置、替换/插入/追加语义、尺寸、必须保留的箭头/回路/层级、原素材处置方式。

遵循 `references/feishu-layout-guide.md`。内容块齐全不代表视觉合格；关系图缺少方向、文字超框、字体过小或位置错误都要返工。

### 8. 双重 QA

使用 `references/qa-rubric.md` 分别执行内容 QA 和视觉/发布 QA。先修复关键失败项，再考虑措辞润色。

必须回查：

- 每条关键结论和待办是否有证据；
- 用户范围、说话人和术语是否全部生效；
- 是否遗漏会改变实现方向的分工、约束或接口；
- 图形是否保留逻辑关系并可阅读；
- 操作计划是否会产生旧图残留、文末重复或错误账号写入。

### 9. 发布或生成待发布包

#### `kala-feishu` 可用

1. 读取目标 URL，验证账号路由和编辑权限；
2. 获取现有块树，标记目标块的 ID、父级和索引；
3. 用自然语言列出要删除、替换、新建和保留的对象；
4. 涉及删除时等待用户明确确认；
5. 按计划精确写入，不默认全量重写或追加；
6. 回读块树、图片尺寸和画板节点；
7. 查看实际渲染，完成视觉 QA。

#### `kala-feishu` 不可用

按 `references/offline-package.md` 生成待发布包并运行：

```bash
node <本 skill>/scripts/validate-package.mjs <纪要包目录>
```

验证通过只代表本地包结构完整，不代表飞书已发布。

### 10. 收尾报告

明确列出：

- 已完成的内容与发布动作；
- 未完成或待确认的事项；
- 内容 QA、视觉 QA、发布回读各自的验证范围；
- 本地包或飞书文档位置；
- 是否需要重启、授权或换设备继续。

不要用“已完成”覆盖未执行的视觉检查或真实发布。

## 快速判断表

| 情况 | 行动 |
|---|---|
| 只有不可访问链接 | 停止并索要转录 |
| 有样例和对应转录 | 先反推方法，再处理新会议 |
| 用户限定月份/阶段 | 锁定范围，未来内容降级为边界 |
| 白板难辨 | 用转录佐证，仍不确定则询问 |
| 图包含流程关系 | 保留箭头、方向和反馈回路 |
| 用户说“替换原图位置” | 读取块树后原位替换，禁止文末追加 |
| 飞书不可用 | 生成并验证本地待发布包 |
| 发布后块数正确 | 仍需检查实际渲染 |

## 常见错误

- 先写总结再补证据：容易遗漏关键结论并把候选方案写实。
- 把样例当内容模板：会让旧会议事实污染新纪要。
- 用“视觉一致”描述内容相同：版式、留白、字体和关系必须单独验证。
- 为了整洁删箭头：会破坏图的逻辑含义。
- 没读块树就改飞书：极易把替换做成追加或删错位置。
- 只验证 API 成功：接口成功不等于页面可读。
- 在无权限设备声称完成：必须区分本地成品与飞书交付。
