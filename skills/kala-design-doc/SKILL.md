# 中文设计文档

在项目规范规定的交付范围内，把功能逻辑写得准确、具体、易读，并删除不产生新信息的内容。不要为了精简改变语义，也不要用通用写作偏好改写项目的文档制度。

## 适用边界

- 只在创建、编辑、改写或审核中文设计文档正文时使用。
- 普通问答、方案讨论、读取文档后回答问题，不进入本文档工作流。
- 技术实现文档和文学写作不属于默认范围；用户或项目明确要求时，按其专属规范处理。
- 本 Skill 约束文档质量，不接管项目的事实源、模板、术语、流程、文件位置和验收制度。

## 第一步：确定工作模式

选择一种模式：

1. **新建**：把已确认需求组织成文档；把未确认内容标为假设或待定，不替用户拍板。
2. **编辑或改写**：以原文语义和既有结构用途为基准；只在文档契约允许时调整结构，不改变事实、规则、边界与确定性。
3. **审核**：只报告疑似问题；除非用户同时要求修改，否则不要直接重写。

## 第二步：建立文档契约

先读取用户要求、现有文档、项目说明、专属 Skill、模板、术语表和事实源索引。上下文已有的信息不要重复询问。

从这些材料中提取本次文档契约：

- **职责**：本文档负责和不负责定义什么。
- **读者**：谁使用它，需要据此理解、决定或执行什么。
- **事实源**：什么是已确认事实，什么只是参考、旧稿、示例或待定想法；记录已知的优先级、版本和生效状态。
- **结构**：必须存在的章节、表格、字段、任务映射、验收项和引用；区分固定格式、固定文案和允许编辑的自由文本。
- **语言**：项目术语、命名、语气、详略和目标读者能够理解的技术层级。
- **流程**：当前阶段、编写步骤、审核方式、文件位置、版本和发布要求。

把契约作为约束使用，不要原样抄进交付文档。现有章节、锚点和并列结构可能承担评审定位、稳定引用或快速查阅用途；在确认没有这些用途前，不主动重组。若关键契约缺失且不同答案会改变职责、核心规则或交付形式，先向用户确认。只有不存在已知冲突且假设不会改变规则或交付要求时，才能用最小假设推进并明确标注。

## 第三步：调和通用规则与项目规则

按以下优先关系执行：

| 情况 | 处理 |
|---|---|
| 项目明确要求 | 按契约完整保留；固定格式和固定文案不改，自由文本区才可改善表达 |
| 项目明确禁止 | 不写 |
| 两者要求方向相同 | 只执行一次，不重复制造章节或检查项 |
| 项目与通用默认值冲突 | 以项目契约为准 |
| 项目材料彼此冲突或事实源不明 | 暂停修改受影响内容及其依赖项，向用户指出冲突；其他独立内容可继续 |
| 项目未规定 | 使用本文后面的通用默认值 |
| 双方都未规定 | 只做低风险表达优化，不发明功能规则或文档制度 |

只有当用户要求、现有文档、项目说明、专属 Skill、模板和事实源都没有形成相关约束时，才算“项目未规定”。

项目要求的重复内容可能承担独立交付用途。例如速览、任务映射、验收表或跨文档引用不能仅因正文已有同一规则就删除。项目规定的表格结构、行列、固定文案和签收信息不得删除；只在项目允许编辑的自由文本区清理无用途的重复表达。

## 第四步：建立语义底账

编辑或大幅改写前，在工作记录中提取必须保留的语义，不要把底账写进交付文档：

- 主体：谁执行、拥有或负责。
- 条件：何时触发、前置条件和适用范围。
- 行为：允许、禁止或必须发生什么。
- 结果：状态、数值、反馈或产出如何变化。
- 边界：例外、失败处理、上限、顺序、优先级和版本范围。
- 确定性：哪些是已确认、建议、示例、假设或待定。

以下变化都属于语义变化，不得伪装成措辞优化：

- 增删或替换主体、条件、行为、结果、边界、数值、顺序或优先级。
- 改变职责归属、功能范围、版本范围或状态转换。
- 把可能、建议或示例改成必须，或反向弱化已确认规则。
- 用更具体的说法补入事实源没有确认的新规则。

发现矛盾、缺口或歧义时，不自行选择解释。只继续处理事实源清晰且不依赖冲突项的内容；冲突项等待用户或项目治理规则裁决。

## 第五步：应用通用质量内核

### 守住职责

逐段检查内容是否属于文档契约规定的职责。越界内容移到正确位置、改成必要引用，或提出待确认问题。不要替项目决定新的文档分工。

### 保证信息增量

除契约要求的固定内容外，每一段都必须增加至少一种内容：新事实、新规则、新边界、必要理由，或导航、追踪、验收等帮助读者完成任务的作用。没有这些作用才合并或删除。

按语义而非字面查重，重点识别：

- 同一规则换一种说法再次出现。
- 标题、引言、正文和小结反复转述同一结论。
- 示例只替换名字，没有增加条件、边界或结果。
- 多个章节重复解释同一职责。
- 表格与正文逐项重复，二者没有不同用途。

同一事实默认只有一个权威定义位置。其他位置可以为速览、导航、任务追踪、验收或角色分工进行映射，但不要伪装成第二份独立定义；契约要求固定复述时按原格式保留。

### 使用读者能懂的功能语言

- 先写结论或规则，再写必要条件、结果和边界。
- 用“条件／主体 → 行为 → 结果”表达功能逻辑。
- 把抽象词翻译成可观察的行为或状态变化；翻译不出来时，把它视为尚未想清的内容。
- 首次出现术语时按项目要求定义；后文固定使用同一称呼。
- 避免“赋能、抓手、链路、闭环、能力建设、统一承载、实现了对……的支持”等没有落到具体行为的表达。
- 在主题、条件、读者任务、可扫读性或模板对照需要变化时分段，不按固定长度机械拆段。

### 控制技术层级

只保留目标读者完成任务所需的技术信息。功能设计默认描述用户可观察的行为、规则、状态和边界；若文档契约要求数据结构、配置字段、接口约束或工程验收信息，则按要求保留，不要以“说人话”为由删除。

### 检查理由和例子

设计理由只在缺失后可能导致读者错误理解或修改规则时保留，并尽量一句说清。例子必须增加新条件、新边界、新结果或容易误解的对照；只复述规则的例子删除。决策记录、评审报告等文档若明确要求备选方案和取舍理由，按契约完整保留。

## 第六步：仅在项目未规定时使用默认值

- 按读者需要完成的理解或决策组织章节，不制造空章节。
- 每个章节承担一个可说明的用途；导航、角色分工、评审定位、稳定引用和快速查阅也算用途，否则才合并。
- 不机械添加背景、价值、总结、下一步或写作过程。
- 不把自检过程写进正文。
- 篇幅服从信息与决策需要，不追求固定字数。

## 第七步：交付前核对

- 输出是否满足文档契约中的职责、结构、术语、流程和交付要求。
- 是否改变了语义底账中的主体、条件、行为、结果、边界或确定性。
- 每段、每个章节和每个例子是否有独有用途。
- 是否仍有语义重复、抽象空话或目标读者不需要的技术细节。
- 所有项目要求的章节、字段、映射和验收项是否仍然完整。
- 项目未规定处是否误添了功能规则或制度。

若修改可能改变语义，停止修改该处并列出：原文、疑似问题、可能影响、需要确认的问题。

## 对话与交付

- 不展示阶段状态、研究摘要、写作思路或逐条自检过程，除非用户要求。
- 新建或编辑完成后，只说明改了哪些类型的内容，以及还有哪些需要用户决定。
- 审核时先给疑似问题摘要；每项按“白话结论 → 一条实际原文或场景 → 为什么有问题”说明。用户认可后再展开。项目验收规范要求完整报告时，按其格式执行。
- 不用函数名、字段名或代码路径证明功能文档问题，除非用户要求技术证据。
