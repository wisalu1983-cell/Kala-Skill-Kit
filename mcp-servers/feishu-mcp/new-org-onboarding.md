# 新组织接入飞书 MCP 工具 - 操作蓝本

基于 2026-07-20 接入「Trumen-COS」这次实操整理。是"下次照着做"的版本,不是流水账——踩过的坑直接写成检查点,不重复叙述当时怎么发现的。

## 前提

- 本机已经部署好这套工具的共享运行时(代码 + `node_modules`),不需要每个组织重新部署一遍,见 `AppInfo.md` 第 4 节。
- 有权限在目标组织的飞书后台创建自建应用,或者能找到愿意配合审核的管理员。

## 步骤 0:先确认这真的是一个新组织,别搞错身份

**这是最容易踩的坑,必须放在最前面。** 开始整套流程之前,先问对方要一份该组织内**任意一篇真实文档的链接**,看链接里的域名(`xxx.feishu.cn`)。

- 域名跟已有配置(见下面"已知组织清单")里任何一条**相同** → 这不是新组织,是同一个飞书账号下的另一个项目/知识空间。不需要新建应用、走审核——直接用已有的那个应用,把这个新文档/知识空间共享给它就行(参考 `AppInfo.md` 里的文档授权说明)。
- 域名跟已有的都**不一样** → 才是真正的新组织,继续走下面完整流程。

不要跳过这一步凭印象判断——这次接入 Trumen-COS 时就因为没做这个检查,一直误以为"原有配置"和最开始那份文档是同一个组织,白白多确认了好几轮才发现搞反了。

## 步骤 1:创建自建应用

1. 用目标组织的账号登录 `open.feishu.cn` → 右上角「开发者后台」
2. 首页「创建企业自建应用」→ 填名称、描述、图标 → 创建
3. 「凭证与基础信息」→ 记下 **App ID** 和 **App Secret**

## 步骤 2:导入标准权限(不用逐个搜索勾选)

「权限管理」→「批量导入/导出权限」→ 导入页签 → 粘贴本目录下 `permission-scopes.json` 的内容 →「下一步,确认新增权限」→「申请开通」。

这份 JSON 是权限点字符串清单,不绑定租户,可以跨组织直接复用。

## 步骤 3:配置 OAuth 重定向 URL(新应用默认没配,必踩的坑)

「安全设置」→「重定向URL」→ 添加:

```
http://localhost:3000/callback
```

不配这一步,后面登录会直接报错"重定向 URL 有误"(错误码 20029)。

## 步骤 4:设置可用范围,发布版本,等审核

「版本管理与发布」→「创建版本」→ 可用范围至少包含操作者自己 → 保存 →「申请线上发布」→ 等管理员(可能是自己,也可能要找人)审核通过。

**这一步通常是全流程耗时最长的环节**,权限和重定向URL可以在等待期间先配好。

## 步骤 5:写入凭证文件

在共享部署目录(如 `D:/CursorLibrary/MCP/FeiShuDoc/`)下新增一对独立命名的文件,不覆盖其他组织的:

- `keys/<组织标签>.json`:`{"app_id": "...", "app_secret": "..."}`
- `data/<组织标签>-token.txt`:不用预先创建,首次 OAuth 登录成功后会自动生成

## 步骤 6:注册 MCP server 配置项

在 `.claude.json` 的 `mcpServers` 里加一条,`args` 跟已有条目指向同一份 `dist/server.js`,只有 `env` 里的凭证路径不同(完整示例见 `AppInfo.md` 第 4 节)。**改完配置需要重启 Claude Code 才会生效连接。**

## 步骤 7:完成 OAuth 登录

调用任意一个只支持 `useUAT: true` 的工具(比如 wiki 搜索),会返回一条授权链接。**这条链接只有 60 秒有效期**,过期需要重新调用生成新的——沟通往返一次基本就会过期,不用意外,直接要求重新生成即可。

## 步骤 8:测试读取,并且再验证一次组织身份

用目标组织的一份真实文档链接测试读取。**读成功之后,再看一眼返回结果里的域名/内容标题是不是真的对得上预期的组织**——不要只看"调用没报错"就认为万事大吉,步骤 0 的身份确认在这里要闭环验证一次。

## 步骤 9:登记到已知组织清单

在 `AppInfo.md` 第 5 节的表格里加一行:组织标签、飞书租户域名、App ID、说明。App Secret 和 token 永远不写进这份文档或仓库。
